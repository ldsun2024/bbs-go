## 摘要

`bbs-go` 是一个 **Go + React 双端一体**的轻量级社区/问答平台，定位于中小规模自托管论坛、知识库与问答社区。项目功能闭环完整（内容、互动、增长、治理、安装、部署均有实现），分层清晰，工程完成度明显高于一般开源论坛项目。

**关键数据**

| 指标 | 数值 |
| --- | --- |
| 后端代码 | 340 个 Go 文件，约 34,303 行 |
| 前端代码 | 282 个 TS/TSX 文件，约 41,299 行 |
| HTTP 路由注册 | 约 255 个（106 GET / 148 POST / 1 DELETE） |
| 数据模型 | 45 个（含 1 张迁移记录表） |
| Service / Repository | 63 个 Service 文件 + 11 个事件处理器；45 个 Repository |
| 前端路由模块 | 54 个（含 18 个后台页面） |
| 测试文件 | 44 个（后端 43 + 前端 1） |
| 数据迁移版本 | 13 个已注册版本 |

**三条主要结论**

1. **架构选型合理，适合单体自托管。** Gin + GORM 的分层（handler → service → repository）执行得比较彻底，缓存、事件、搜索、上传、权限都做了独立抽象；安装向导、Docker 多阶段构建、双数据库支持使其开箱成本很低。
2. **当前形态是"单实例优先"设计。** 会话缓存、实体缓存、Bleve 全文索引、cron 定时任务全部在进程内，没有 Redis 或外部搜索；一旦部署多副本会出现登录态/权限不同步、搜索分片不一致、定时任务重复执行。
3. **主要短板不在功能，而在"工程护栏"与"安全细节"。** CI 只构建不跑测试，缺少统一的限流/可观测性方案，Cookie 安全属性、SSR 错误输出、上传大小上限等存在可修复的具体问题；未发现无需认证即可远程利用的高危漏洞。

**风险评级**：低到中。适合中小规模自托管与二次开发；不适合直接用于多副本高可用或强合规场景。

### 3.3 请求处理链路

以"发帖"为例：

```
POST /api/topic/create
  → InstallMiddleware        检查是否已安装（未安装返回 428）
  → AuthMiddleware           解析 token，注入 currentUser（不强制登录）
  → TopicCreate handler      参数绑定 + 登录校验 + 反垃圾策略
  → AntiAbuseService         用户/IP 发布频控（查最近时间窗内的内容数）
  → TopicPublishService      事务：写 topic、投票、标签、计数、附件、悬赏扣分
  → search.UpdateTopicIndexAsync  异步写 Bleve
  → event.Send(TopicCreateEvent)  异步派发任务/通知
  → ginx.WriteJSON           统一响应包 { success, data, message, errorCode }
```

对应代码：`internal/middleware/install_middleware.go:12`、`internal/middleware/auth_middleware.go:11`、`internal/handlers/api/topic_handlers.go:125`、`internal/services/topic_publish_service.go:28-151`。

## 四、后端子系统分析

### 4.1 认证与账号

支持的登录方式：

- 用户名/邮箱 + 密码（bcrypt 校验）
- 邮箱验证码、短信验证码
- 微信、Google、GitHub、OIDC
- 图形验证码 / 旋转拼图验证码

实现特点：

1. **会话 Token 是随机 UUID，不是 JWT。** `UserToken` 表保存明文 token，`ExpiredAt` 控制有效期，默认 7 天（`constants.DefaultTokenExpireDays`），可通过系统配置调整。
2. **Token 读取有三个来源**：查询参数 `userToken`、Cookie `bbsgo_token`、Header `Authorization: Bearer` 或 `X-User-Token`（`user_token_service.go:115-131`）。
3. **密码策略统一**：注册、改密、安装管理员都走 `validate.IsPassword`，避免安装入口成为弱口令后门。
4. **第三方账号绑定**：`ThirdUser` 以 `(openId, thirdType)` 唯一，`OIDCIdentity` 以 `(issuer, subject)` 唯一，避免重复绑定。
5. **每日登录事件**：登录态访问时通过布隆过滤器按天去重，触发 `user.login` 任务事件（`user_token_service.go:62-83`）。

> `internal/pkg/token/user_token.go` 中存在一套未被引用的 JWT 实现，属于历史遗留死代码，但 `golang-jwt/jwt` 仍保留在 `go.mod` 直接依赖中。

### 4.2 权限与后台治理

- 权限定义集中在 `internal/permissions/permissions.go`，共 **60 个权限点**，按 workspace / content / community / growth / system / logs 分组。
- 后台鉴权采用"**方法 + 路径模式**"映射到权限码（Ant 风格通配），例如：
  - `POST /api/admin/topic/delete` → `dashboard.topic.delete`
  - `POST /api/admin/user/forbidden` → `dashboard.user.forbidden` 或 `dashboard.user.forbiddenForever`
- 未登记的路径默认拒绝（fail-closed），避免新增后台接口漏配权限；`owner` 角色直接放行（`admin_middleware.go:14-32`）。
- 权限码会生成前端常量文件 `web/lib/auth/permissions.generated.ts`，由 `cmd/generator/permissions` 产出，减少前后端字面量漂移。
- 后台菜单与页面级校验在前端 `RequireDashboardAdmin` 组件完成，服务端仍是最终防线。

**注意点**：owner 直通会掩盖权限规则缺失的问题。普通管理员账号才能暴露"接口未登记"的故障，建议在 CI 中用普通管理员做一次路由覆盖检查。

### 4.3 内容模型

内容域是项目的核心，包含三类主体：

| 类型 | 模型 | 说明 |
| --- | --- | --- |
| 话题 | `Topic` | `type=0` 帖子、`type=1` 动态、`type=2` 问答 |
| 文章 | `Article` | 长文/知识库，支持 Markdown/HTML、封面、审核 |
| 评论 | `Comment` | 多态：`entityType + entityId`，可评论话题/文章/评论 |

配套能力：

- **节点**：`Category` 支持一级/二级（`parentId`），并有 `normal` / `qa` 类型，问答节点只能发问答帖。
- **标签**：`Tag` + `TopicTag` / `ArticleTag`，发帖时按名称 `GetOrCreates`。
- **投票**：`Vote` / `VoteOption` / `VoteRecord`，支持单选/多选、截止时间、每人唯一。
- **问答**：`QaStatus`、`AcceptedCommentId`、`BountyScore`；采纳答案给回答者加分，删帖未采纳则退回悬赏。
- **隐藏内容**：`Topic.HideContent`，评论或作者本人才能通过 `/api/topic/hide_content` 获取（`topic_handlers.go:479-501`）。
- **附件**：`Attachment` + `AttachmentDownloadLog`，支持下载扣积分、重复下载不扣分。
- **审核**：`status=2` 待审核；后台可审核话题/文章；待审核内容不计入用户发帖数。
- **反滥用**：`AntiAbuseService` 按用户/IP 统计时间窗内发布数量，可配置"拒绝"或"转审核"。
- **违禁词**：`ForbiddenWord` 支持普通词与正则。

### 4.4 增长体系

这是项目相对同类产品的差异化能力，设计完整度较高：

| 能力 | 实现 | 关键设计 |
| --- | --- | --- |
| 签到 | `CheckIn` | 每人一条记录，记录连续天数与最后签到日 |
| 任务 | `TaskConfig` + `UserTaskEvent` + `UserTaskLog` | 事件驱动；周期键（终身/日/周/月/年）；唯一索引防重复发奖 |
| 积分 | `User.Score` + `UserScoreLog` | 所有增减都有流水，来源类型可追溯 |
| 经验/等级 | `User.Exp` + `UserExpLog` + `LevelConfig` | 累计经验严格递增；升级发事件 |
| 勋章 | `Badge` + `UserBadge` | `(userId, badgeId)` 唯一，来源可记录 task/log |
| 关注/粉丝 | `UserFollow` | 双向状态 `none/follow/both` |
| 信息流 | `UserFeed` | 按关注关系写入，供关注流查询 |
| 消息 | `Message` | 站内信，可按类型开关；同时支持邮件通知 |

任务引擎的执行路径：

```
业务事件（发帖/评论/签到/关注/点赞/收藏/登录/采纳）
  → event.Send
  → task_event_handler
  → TaskEngineService.HandleUserEvent
      → 查 TaskConfig(eventType)
      → 事务内更新 UserTaskEvent 进度
      → 达成则写 UserTaskLog + 发积分/经验/勋章
```

对应代码：`internal/services/eventhandler/task_event_handler.go`、`internal/services/task_engine_service.go:73-103`。

### 4.5 搜索

- 使用 Bleve 内嵌索引，索引文档分 `topic` / `article` / `user` 三类。
- 支持关键词、分类、时间范围、推荐筛选、高亮。
- 写索引时机：发帖/改帖后异步 goroutine；用户/文章更新时同步写。
- 后台提供"重建索引"接口与状态查询。

**结构性限制**：索引是本地目录（`config.Search.IndexPath`），多副本无法共享；`search.Init()` 在非"索引不存在"错误下只记录日志，`index` 可能为 nil，后续写入会 panic（`internal/pkg/search/search.go:28-38`）。

### 4.6 上传与存储

- `Uploader` 接口只有两个方法：`PutObject`、`CopyImage`，实现包括本地、阿里云 OSS、腾讯 COS、AWS S3、通用 S3（兼容 R2/MinIO/RustFS）。
- Key 规则：`images/yyyy/MM/dd/{md5|uuid}.ext`、`attachments/yyyy/MM/dd/{uuid}.ext`；非生产环境自动加 `test/` 前缀。
- 图片上传做了**内容嗅探**：只允许 jpeg/png/gif/webp/bmp/x-icon，明确排除 SVG，防止伪装成图片的 HTML/脚本（`internal/services/upload_service.go:20-50`）。
- 附件上传按扩展名白名单校验，并限制大小与数量（可配置）。
- 远程图片 `CopyImage` 会下载后重新上传，降低外链失效与 SSRF 面（下载地址仍由服务端发起，需注意内网地址过滤）。

### 4.7 数据访问与迁移

- 表名前缀 `t_`、单数命名（`schema.NamingStrategy`）。
- 时间统一使用**毫秒时间戳 int64**，而非 `DATETIME`，跨数据库行为一致。
- 无数据库外键，关联完整性由应用层保证；删除以 `status` 软删除为主。
- 计数器冗余在 `User.topicCount`、`Topic.commentCount` 等字段，读多写少场景性能好，但需要所有写路径严格维护。项目已针对删除/审核/恢复做过一致性修复，并有 `topic_count_test.go` 覆盖。
- 迁移分两层：
  1. 启动时 `AutoMigrate(models.Models...)` 自动建表/加列；
  2. `migrations` 包按版本执行数据迁移，记录成功/失败/重试次数。

### 4.8 定时任务与 SEO

- `scheduler.Start()` 只在 `BBSGO_ENV=prod` 时启动（`internal/install/install.go:512-520`）。
- 目前只有一个任务：每天 04:00 生成并上传 Sitemap（`internal/scheduler/cron.go:14-18`）。
- Sitemap 生成支持分批（每批 1 万）、并发保护、状态查询，结果写入对象存储，`/sitemap.xml` 302 到实际地址。

### 9.2 P1 问题详述

#### R1 图片上传上限实际为 10 GiB

```go
// internal/models/constants/constants.go:6-7
UploadMaxM                   = 10
UploadMaxBytes         int64 = 1024 * 1024 * 1024 * UploadMaxM
```

`UploadMaxM` 的语义是 MB，但计算使用了 `1024^3`，结果约为 10.7 GB。`upload_handlers.go:32` 用它做校验，提示语却是"最大 10"。虽然 `FormFile` 会落临时文件、不会一次性全读入内存（仅在 `Size<=0` 时回退读内存），但单请求仍可写满磁盘并长时间占用连接。

建议：改为 `UploadMaxM * 1024 * 1024`，并把上限做成系统配置；同时在反向代理层设置 `client_max_body_size` 兜底。

#### R2 SSR 错误页泄露堆栈

```js
// web/scripts/serve-ssr.mjs:125-130
} catch (error) {
  res.statusCode = 500
  res.end(error instanceof Error ? error.stack : String(error))
}
```

生产环境应返回固定错误页/JSON，堆栈只写服务端日志，并附带 requestId 便于关联。

#### R3 会话 Cookie 与 Token 传递面

```go
// internal/pkg/ginx/context.go:67
ctx.SetCookie(name, value, maxAge, "/", "", false, options.httpOnly)
```

第 6 个参数是 `secure`，硬编码为 `false`，且未设置 `SameSite`。另外 `user_token_service.go:116` 允许从查询参数 `userToken` 读取令牌，令牌可能进入访问日志、浏览器历史、Referer。

建议：
- 生产强制 `Secure`，按部署形态设置 `SameSite=Lax`（纯 API 跨站场景用 `None; Secure`）；
- 移除查询参数取 Token 的兼容逻辑，或仅在明确的下载/嵌入场景使用一次性签名；
- 增加 Token 轮换与"退出所有设备"能力。

#### R4 CI 缺少质量门禁

`.github/workflows/main.yml` 只有 `pnpm install` + `make package`；`docker-image.yml` 只有构建与推送。没有任何 `go test`、`pnpm lint`、`pnpm typecheck` 步骤。

建议：增加一个 PR/push 工作流，至少执行：
1. `go vet ./...` + `go test -tags dev ./...`（或按包分组）；
2. `cd web && pnpm install --frozen-lockfile && pnpm typecheck && pnpm lint`；
3. 可选：`go test -race` 跑核心包。

#### R5 事件总线可能静默丢事件

```go
// internal/pkg/event/event.go:20
eventPool, err = ants.NewPoolWithFunc(4, dispatch, ants.WithMaxBlockingTasks(1000))
...
func Send(e any) {
    if err := eventPool.Invoke(e); err != nil {
        slog.Error(err.Error(), slog.Any("err", err))
    }
}
```

高峰期队列满时 `Invoke` 返回错误，事件被丢弃，调用方无感知。受影响的副作用包括：任务进度、积分/经验发放、勋章、站内信、搜索索引。

建议：
- 关键副作用改为事务内直接执行或落"事件表/outbox"，由后台消费者重试；
- 至少增加丢弃计数指标与告警；
- 池大小与队列长度可配置。

#### R6 单实例耦合

| 组件 | 现状 | 多副本后果 |
| --- | --- | --- |
| `UserTokenCache` | 进程内 LoadingCache，60 分钟过期 | 退出登录/禁用后其他副本仍认旧 Token |
| 实体缓存 | 进程内 | 后台改配置/权限后其他副本延迟生效 |
| Bleve | 本地目录 | 各副本索引不一致，搜索结果漂移 |
| cron | 每个实例都启动 | Sitemap 重复生成 |
| 发布频控 | 基于数据库 COUNT | 多副本仍可用，但成本随副本线性增加 |

若短期不引入 Redis，应明确"单副本部署"约束，并在部署文档与健康检查中体现。

#### R7 无优雅停机

`newRouter().Run(":"+port)` 直接阻塞，没有捕获 `SIGTERM`，也没有 `server.Shutdown(ctx)`。容器编排滚动更新时，在途请求会被直接切断；正在执行的事务可能回滚，但客户端看到 502/连接重置。

建议：改用 `http.Server` + `signal.NotifyContext` + `Shutdown`，并让 `entrypoint.sh` 先向两个子进程发 TERM、等待退出。

#### R8 付费附件可被直链绕过

- 下载接口 `/api/attachment/download/:id` 会校验登录、扣积分、写下载记录，然后 302 到 `att.FileUrl`。
- 本地存储的 `FileUrl` 是 `/res/uploads/attachments/...`，而 `router.go:58` 将整个 `/res` 目录公开为静态文件。
- 因此任何人拿到该 URL 即可跳过积分与登录直接下载。UUID 降低了被猜测的概率，但 URL 会出现在日志、聊天转发、浏览器历史中。

建议：
- 本地附件改为经鉴权的流式下载（`/api/attachment/stream/:id`），不暴露物理路径；
- 或使用短时效签名 URL（OSS/COS/S3 均支持）；
- `/res` 目录拆分：公开图片与私有附件分开挂载。

### 9.3 P2 问题说明（摘要）

- **R9 安全响应头**：全仓库检索不到 CSP/XFO/HSTS/Referrer-Policy。建议在 Gin 中间件或前置 Nginx 统一注入；注意脚本注入功能需要 nonce/hash 策略。
- **R10 容器与默认口令**：Dockerfile 未创建非 root 用户；compose 默认 `bbsgo_password`/`bbsgo_root_password`。建议增加 `USER`、强制首次安装修改口令、在 README 标注必须覆盖默认值。
- **R11 配置文件权限**：`os.WriteFile(configFile, yamlData, 0644)`。建议 `0600`，并支持从环境变量/Secret 注入数据库口令。
- **R12 ID 混淆**：`idcodec.Decode` 先尝试 `cast.ToInt64`，纯数字直接通过。若目的只是"URL 美观"可接受；若声称防枚举则不成立。建议明确语义，或在对外接口只接受编码 ID。
- **R13 AutoMigrate**：生产每次启动都做全模型迁移，表大时耗时且可能锁表。建议生产关闭自动迁移，改用版本化 SQL/GORM Migrator，并在发布流程中显式执行。
- **R14 HTTP 语义**：业务失败统一 200，导致监控、网关重试、CDN 缓存都难以按状态码处理。建议至少区分 4xx（参数/权限）与 5xx（系统错误），保留 `errorCode` 做细分。
- **R15 可观测性**：没有 metrics、trace、requestId、独立健康检查。建议引入 Prometheus 指标（QPS、延迟、错误率、事件丢弃数、DB 连接池）、OpenTelemetry trace、`/healthz`。
- **R16 列表 N+1**：`BuildSimpleTopics` 每条话题都会查分类、标签、投票；同时每条都做一次 Markdown 渲染取摘要。建议批量查询（`IN`）+ 缓存分类/标签 + 列表页只存纯文本摘要。
- **R17 搜索写入**：`TopicService.Updates/UpdateColumn` 同步写 Bleve，且 `search.Init` 失败时 `index` 为 nil。建议索引写入异步化、初始化失败直接 fail-fast，并提供索引不可用时的降级策略。
- **R18 附件中间件**：每次请求都查 `t_attachment`。建议缓存文件名或把 `Content-Disposition` 在写入时持久化到对象元数据。
- **R19 接口契约**：没有 OpenAPI。建议从 handler/DTO 生成 spec，并用契约测试校验前后端字段。
- **R20 前端大组件与测试**：`dashboard.settings.tsx` 近 100 KB，建议按配置分组拆分；引入 Vitest + Playwright 覆盖登录、发帖、后台关键流程。
- **R21 文档漂移**：见 8.5。
- **R22/R23/R24**：清理死代码与依赖；修正常量命名与硬编码文案；示例配置改为具体来源白名单。

## 十一、适用性评估

### 适合

- 中小型技术社区、问答社区、知识库、企业内部社区。
- 希望**单机/小规模自托管**、偏好 Go 技术栈、需要论坛 + 问答 + 文章一体化的团队。
- 需要开箱即用的用户成长体系（签到、任务、积分、等级、勋章）的运营型社区。
- 需要二次开发但不想从零搭建账号、权限、内容、后台的项目。

### 不适合（或需要额外投入）

- 需要多副本高可用、跨机房部署的场景：当前缓存、搜索、定时任务均为单进程语义。
- 强合规场景（等保、金融级审计）：缺少集中审计、密钥管理、细粒度数据权限、WAF/限流配套。
- 超大规模内容量（百万级以上帖子）：列表 N+1、同步索引写入、`COUNT` 频控会成为瓶颈，需要专门优化。
- 需要开放平台/第三方生态：缺少 OpenAPI、OAuth Provider、Webhook、插件机制。

### 二次开发建议

1. 先读 `internal/server/router.go` 建立接口全景，再按 `handlers → services → repositories` 追业务。
2. 新增后台接口时，必须同步在 `internal/permissions/admin_permission_registry.go` 登记，否则普通管理员会 403（owner 不受影响，容易漏测）。
3. 修改计数、积分、经验等冗余字段时，务必在同一个事务内完成，并补充对应 `*_test.go`。
4. 前端改动后至少执行 `pnpm typecheck` 与 `pnpm lint`；后端改动执行 `go test -tags dev ./...`。
5. 本地开发用 `make dev`（Go 带 `dev` 标签 + Vite），避免必须先构建 SPA。
