## 前端 pnpm 版本踩坑（已解决）

- 现象：`cd web && pnpm install --frozen-lockfile` 报 `ERROR packages field missing or empty`；`pnpm run` 同样报错。
- 根因：本机全局 pnpm 是 9.15.9（`C:\Users\Administrator\AppData\Roaming\npm\pnpm.ps1`），而项目 `packageManager` 要求 10.30.2。`web/pnpm-workspace.yaml` 只有 `onlyBuiltDependencies`/`allowBuilds`、没有 `packages` 字段，pnpm 9 强制要求该字段，pnpm 10 允许省略。
- 解决：`corepack pnpm install --frozen-lockfile` 成功（736 packages，13.1s，锁文件未变）；`corepack pnpm -v` = 10.30.2。corepack 已可用，但 PATH 中 npm 全局 shim 优先，`corepack enable` 不一定能覆盖。
- 长期方案：`npm i -g pnpm@10.30.2` 覆盖全局；或所有前端命令统一用 `corepack pnpm <cmd>`。已在 `docs/启动命令手册.md` 的 1 节与 10.8 节补充。
- npm 兼容性（已补到手册 10.9 节）：依赖装好后 `npm run dev` / `build:ssr` / `start` / `typecheck` / `lint` 可用；`npm run build` 内部调用 `pnpm build:ssr`（pnpm 9 会失败）；`npm run build:spa` 在 Windows 因 POSIX 环境变量语法失败；`npm install` 不建议（生成 package-lock、忽略 pnpm-lock，npm 还会告警 `.npmrc` 的 only-built-dependencies）。

- **启动坑（已修）**：`AutoMigrate` 在 `t_o_id_c_identity` 报 `Error 1071 Specified key was too long; max key length is 3072 bytes`。根因：`models.OIDCIdentity` 的 issuer/subject 为 `size:512`，而库里旧表是 255，`ALTER TABLE ... MODIFY issuer varchar(512)` 时联合唯一索引 `uk_oidc_issuer_subject(provider_key, issuer, subject)` 变成 (64+512+512)×4=4352 B > 3072。
  - 修复：`DROP INDEX uk_oidc_issuer_subject` → 两列 MODIFY 到 512 → 重建为前缀索引 `(provider_key, issuer(350), subject(350))` = 3056 B。
  - 该表 0 行数据，无丢失风险。GORM 的 HasIndex 只按索引名判断，前缀索引不会被反复重建。
  - **遗留隐患**：这是代码侧问题 —— 全新 MySQL 库按 `size:512` + 三列联合唯一索引建表必然超 3072 B，重装/新环境会再次失败。彻底修法是给 tag 加 `length:350` 或把 size 降到 255。
